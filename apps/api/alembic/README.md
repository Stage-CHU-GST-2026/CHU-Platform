# Database Migrations with Alembic

This project uses **Alembic** with **async SQLAlchemy** and **PostgreSQL** to manage database schema changes.

---

## Quick start

### Prerequisites

PostgreSQL must be running:

```bash
docker compose up -d postgres
```

### Apply all pending migrations

```bash
cd apps/api
uv run alembic upgrade head
```

### Check current migration status

```bash
uv run alembic current
```

### View migration history

```bash
uv run alembic history
```

---

## Common workflows

### Creating a new migration (autogenerate)

After editing an ORM model in `src/api/models/`, generate a new migration:

```bash
uv run alembic revision --autogenerate -m "description of the change"
```

This compares your models against the actual database and produces a migration script in `alembic/versions/`. **Always review the generated script** before applying it.

### Creating an empty migration (manual)

```bash
uv run alembic revision -m "description of the change"
```

Useful for data migrations, index changes, or raw SQL that autogenerate can't produce.

### Rollback one migration

```bash
uv run alembic downgrade -1
```

### Rollback to a specific revision

```bash
uv run alembic downgrade <revision_id>
```

### View the SQL without running it (offline mode)

```bash
uv run alembic upgrade head --sql
```

## How it works

| File / Folder | Purpose |
|---|---|
| `alembic.ini` | Config file — contains a placeholder DB URL (actual URL comes from `Settings`) |
| `alembic/env.py` | Environment setup — reads `DATABASE_URL` from `api.config.Settings`, imports all models, configures async engine |
| `alembic/script.py.mako` | Template for new migration scripts |
| `alembic/versions/` | The actual migration scripts — **commit these to git** |
| `api/database.py` | SQLAlchemy engine & `Base` referenced by Alembic |
| `api/models/` | ORM models that Alembic reads for autogenerate |

The database URL is resolved from `api.config.Settings` at runtime, which reads from your `.env` file or environment variables — never from `alembic.ini`.

## Common issues

### `sqlalchemy.exc.OperationalError: could not connect to server`

PostgreSQL isn't running. Start it:

```bash
docker compose up -d postgres
```

### `FAILED: Can't locate revision identified by ...`

Your local database is out of sync with the migration history. Reset to the latest:

```bash
uv run alembic stamp head
```

### `Target database is not up to date`

Someone else pushed new migrations. Run:

```bash
uv run alembic upgrade head
```

### Autogenerate doesn't detect my model changes

Make sure your model is **imported** in `alembic/env.py` so `Base.metadata` is fully populated:

```python
from api.models.conversation import Conversation, Message
```

Also check that the model inherits from `api.database.Base` (not a different `Base`).

### Autogenerate tries to drop and recreate tables every time

This usually means Alembic can't match your model to the existing table. Common causes:

- A column has `server_default` in the model but the DB column has a different default
- A `String` column lacks a length in the model but has one in the DB
- Boolean vs integer column mismatches

Fix: add explicit types/defaults in the model, or manually edit the generated migration.

### `ModuleNotFoundError: No module named 'api'`

Run the Alembic command from the `apps/api` directory (so the `prepend_sys_path = src` in `alembic.ini` picks up the right path):

```bash
cd apps/api
uv run alembic upgrade head
```

### Downgrade fails with `ForeignKeyViolation`

Data in the database references rows that would be deleted by the downgrade. You may need to write a custom data migration in the downgrade function, or clean up the data manually first.

## Tips

- **Always review autogenerated migrations** before applying them — Alembic can miss things or generate overly broad changes.
- **Commit migration scripts** (`alembic/versions/*.py`) along with model changes so the whole team stays in sync.
- **One migration per schema change** — keep them small and focused for easier rollbacks.
- **Test both `upgrade` and `downgrade`** locally before pushing.
